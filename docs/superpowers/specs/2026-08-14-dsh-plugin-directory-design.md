# DSH Plugins 产品说明

## 1. 产品概述

DSH Plugins 是面向 DeepSeek Harness 用户的插件搜索与发现网站。它从 GitHub 自动发现带有 `dsh-plugin` topic 的公开仓库，帮助用户按需求、分类和关键词快速找到可用插件。

第一阶段的目标是成为 DeepSeek Harness 的插件索引入口：用户能发现、理解并复制插件的 GitHub 地址或安装命令；不承担插件提交、人工审核、账号体系或站内安装。

## 2. 目标与非目标

### 目标

- 让 Harness 用户快速找到满足当前任务的插件。
- 以分类、搜索和标签降低插件发现门槛。
- 自动同步 GitHub 数据，降低运营成本。
- 给用户足够的信息判断插件是否可信、活跃和适配。
- 形成可被搜索引擎收录的独立插件详情页，为网站积累自然流量。

### 非目标（第一阶段）

- 不提供插件提交入口或人工审核后台。
- 不提供账号、收藏、评论、评分或站内社区。
- 不在站内托管插件代码，也不代替 GitHub。
- 不承诺所有带 `dsh-plugin` topic 的仓库都是真正可用的 Harness 插件。

## 3. 目标用户

### 主要用户：插件使用者

使用 DeepSeek Harness，希望按任务找到现成插件的人。例如需要浏览器自动化、文件处理、Agent 编排、图片理解或通知协作能力的用户。

他们最常见的路径是：按类别浏览或搜索关键词 → 对比简介、标签和活跃度 → 进入插件详情 → 复制 GitHub 地址或安装命令。

### 次要用户：插件开发者

开发者当前主要从自然收录中获得曝光；后续可以再增加提交、认领和维护资料的能力。

## 4. 数据策略

### 数据源

GitHub Search API，查询条件为 `topic:dsh-plugin`。同步的仓库必须为公开仓库。

已验证该 API 可以返回仓库名、所有者、描述、Stars、Forks、语言、License、是否归档、默认分支、更新时间和 topics；topic 结果约有 1,226 个仓库，且由仓库维护者自行标注，因此存在噪声。

### 同步流程

```text
GitHub Search API
  → 仓库基础数据同步
  → README / topics 解析
  → 自动分类与标签提取
  → 活跃度和质量状态计算
  → 自有数据库
  → 搜索索引与前端页面
```

- 定时任务拉取 topic 下的仓库并按仓库更新时间增量更新。
- 保存 GitHub 原始字段和规范化后的展示字段。
- 仓库被删除、改为私有或不再带 topic 时，保留历史记录并标为不可用，不直接删除详情页。
- GitHub 请求失败、限流或单个 README 解析失败时，保留上一次成功数据，并记录同步状态。

### 自动质量提示

不做人工审核，但提供自动状态，避免将 topic 当成官方认证：

- `Active`：近期有代码更新。
- `New`：近期首次发现。
- `Popular`：Stars 达到设定阈值。
- `Archived`：GitHub 已归档。
- `Unclear`：README、topics 或目录结构未能识别出明确插件使用方式。

状态是提示，不是“官方认证”或安全保证。

## 5. 分类体系

首页默认、完整展示以下 12 个分类。一个插件可属于多个分类，但必须选定一个主分类用于主列表展示。

1. 基础与系统
2. 工具集
3. Agent 与自动化
4. Web UI 增强
5. 桌面与终端
6. 视觉与多模态
7. 记忆、知识与学习
8. 安全、诊断与运维
9. 文件与内容处理
10. 通知与协作
11. 搜索与研究
12. 其他

分类由 GitHub topics、README 关键词、目录和配置文件自动推断。分类规则应可配置和可追溯：详情页应显示当前归类使用的标签，但不向用户暴露复杂的内部评分公式。

## 6. 信息架构与交互

### 首页

页面结构固定为：

```text
顶部导航
  → 搜索栏
  → 12 个分类卡片（始终可见）
  → 当前分类的插件结果
```

- 首页不提供“提交插件”入口。
- 默认展示所有 12 个分类卡片，卡片显示分类名称和插件数量。
- 用户点击分类卡片后，不离开首页，在分类区下方更新该分类的插件结果。
- 选中的分类使用黑底白字标记；URL 保存当前分类和排序条件，支持刷新、分享、浏览器返回。
- 搜索支持按插件名、描述、能力和标签匹配；有搜索词时，结果区域展示匹配结果，同时保留分类区。

### 分类结果列表

- 每个分类在首页最多展示 20 个插件。
- 分类总数小于或等于 20 时，展示全部插件，不显示按钮。
- 分类总数大于 20 时，展示前 20 个，并显示“查看更多（剩余数量）”。
- “查看更多”进入对应分类的完整结果页，保留筛选与排序条件。
- 点击整个插件行进入该插件的独立详情页。

每个插件行必须包含：

- 插件名和 GitHub 作者/组织。
- 一行可截断的简介。
- 主分类与辅助标签。
- 主要编程语言。
- Stars。
- 活跃状态（例如 Active、New、Archived）。

默认排序为 Trending；完整结果页可支持 Popular、Recently updated、Recently added 三种排序。

### 插件详情页

详情页提供：

- 插件名称、GitHub 作者/组织、简介和分类标签。
- GitHub 仓库完整地址及一键复制按钮。
- 由 README 或规范化字段提取的安装命令及一键复制按钮。
- README 中截取的使用说明；无法解析时明确显示“请查看 GitHub README”。
- Stars、Forks、语言、License、最近更新时间、默认分支和活跃状态。
- 打开 GitHub 的外链，作为备用入口。
- 相关插件推荐。

复制 GitHub 地址和安装命令不需要跳转 GitHub。复制失败时应显示可恢复提示，并允许用户手动选中内容。

## 7. 视觉与内容规范

- 视觉方向：极简黑白开发者工具风格。
- 页面以清晰文字、边框、留白和信息层级建立视觉，而非依赖渐变、彩色状态条或大面积插画。
- 黑色仅用于主要操作、当前分类和重点内容；灰色用于辅助信息与边框。
- 分类卡片和结果列表以信息可扫描性优先，避免营销性内容占据首页。
- 文案采用简洁、明确的技术产品语言。GitHub 数据原文可保留英文，不强制机器翻译。

## 8. MVP 技术边界

推荐采用“GitHub 定时同步 + 自有数据库 + 搜索索引”的架构，而不是前端直接请求 GitHub API。

原因：

- 避免用户访问触发 GitHub API 限流。
- 提高搜索、分类和详情页加载速度。
- 支持缓存、增量同步、自动分类和 SEO。
- 为后续收藏、提交、认领和数据运营保留扩展空间。

初期可使用单一数据库保存仓库、分类、标签和同步状态；搜索量增长后再将全文搜索独立为专用索引服务。

## 9. 验收标准

- 首页加载后可见搜索栏和完整 12 个分类。
- 点击任意分类，不刷新整个页面即可更新下方结果，并正确更新 URL。
- 分类结果最多显示 20 条；第 21 条及以后只能通过“查看更多”进入完整列表。
- 每条结果展示插件名、作者、简介、分类/标签、语言、Stars 和状态。
- 点击结果进入对应详情页。
- 详情页可一键复制 GitHub 地址和安装命令，复制成功与失败均有明确反馈。
- GitHub 同步失败时，前台仍展示最后一次成功同步的数据，并提示数据更新时间。
- 已归档、不可访问或分类不明确的仓库不会被伪装为已验证可用插件。

## 10. 后续迭代（不属于 MVP）

- 开发者提交与仓库认领。
- 用户收藏、使用记录与推荐。
- 自动兼容性检测和安装成功率。
- 版本历史、更新提醒和安全扫描。
- 多语言界面与中文插件说明增强。
